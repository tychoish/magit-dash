#+title: diff-review/1 interchange contract

The review JSON file is the interchange format between =diff-review= (the review front end), magit-dash, and code-review. Core fields are defined by [[https://github.com/xiaoxinghu/diff-review][diff-review]] and never change here. Extension keys are optional additions; consumers must ignore keys they do not know, and writers must preserve keys they do not understand.

Fixtures: =test/fixtures/review-plain.json=, =review-remote-threads.json=, =review-draft.json=, =review-mixed.json=. Round-trip tests: =test/test-magit-dash-review-contract.el=.

* Core fields (=diff-review/1=)

| Key        | Type   | Meaning                                                                                  |
|------------+--------+------------------------------------------------------------------------------------------|
| =format=   | string | Always ="diff-review/1"=.                                                                |
| =root=     | string | Worktree directory, with trailing slash.                                                 |
| =base=     | string | Base ref.                                                                                |
| =head=     | string | Branch followed, or a commit for a fixed range. Omitted means review the live worktree.  |
| =viewed=   | object | Path to blob hash at which the file was viewed. A mark clears when the blob changes.     |
| =comments= | array  | Comment threads (below).                                                                 |
| =verdict=  | object | Optional. =state= (=changes=, =approved= or =comment=), =head= (full hash), =by=, =at=. Submit adds =submitted_state=, =submitted_head=, =submitted_at= (see Submit). |

Each comment is a thread:

| Key        | Type            | Meaning                                                                    |
|------------+-----------------+----------------------------------------------------------------------------|
| =id=       | string          | Local id.                                                                  |
| =path=     | string          | Optional; absent means a comment on the whole review.                      |
| =lines=    | array of 2 ints | Optional. First and last line, inclusive, counted in the content =blob= names.       |
| =blob=     | string          | Blob hash of =path= when the comment was written.                          |
| =author=   | string          |                                                                            |
| =at=       | string          | ISO 8601 timestamp.                                                        |
| =body=     | string          |                                                                            |
| =replies=  | array           | Optional. Flat list of =author=, =at=, =body= (plus =id=, =gh_comment_id= from magit-dash). |
| =resolved= | boolean         | Optional. JSON =true= or =false=. Parsed with =:false-object :false=.                |
| =outdated= | boolean         | Optional; set when GitHub reports the thread outdated.                     |

* magit-dash keys (already in use)

Written by =magit-dash-review-json-transcode-thread= and =magit-dash-review-json-merge=.

- Top level =magit_dash=: =provider= (="github"=), =repo=, =number=, =url=, =worktree=, =head_oid=, =base_oid=, =synced_at=. Rebuilt on every merge.
- Per comment: =gh_thread_id=, =gh_comment_id=, =gh_resolved=, =origin=. =gh_comment_id= is a string and may be ="" when the first comment has no id; replies carry it once published.
- =origin= values written by the code: =github= (transcoded or submitted threads), =agent= (agent-created comments), =code-review= (comments imported from code-review). =local= is only /read/ by =--merge-json= (to retain a thread); the code does not currently write it, so treat it as reserved for locally authored threads.

* Extension keys

All optional.

| Where                    | Key                   | Type / meaning                                                       |
|--------------------------+-----------------------+----------------------------------------------------------------------|
| top level                | =code_review=         | Object: =pullreq_id= (string), =account=, =analysis=.                |
| =code_review.analysis=   | by path, then by hunk | =rank= (integer), =tags= (strings such as =NO-TEST=), =criteria= (ids). |
| each comment             | =cr_id=               | Integer; code-review's comment id.                                   |
| each comment             | =remote_id=           | String; GitHub node id once sent. May differ from =gh_comment_id=.   |
| each comment             | =status=              | =draft=, =pending= or =sent=.                                        |

=pullreq_id= is the chosen spelling (snake_case, like every other JSON key). =cr_id= is an integer while =remote_id= and =pullreq_id= are strings.

Proposed convention, to be confirmed by the json-adapter task: the hunk key under =code_review.analysis.<path>= is the zero-based hunk index as a string (="0"=, ="1"=, ...).

Distinct from the core =resolved= flag, =gh_resolved= records GitHub's state and =resolved= may be changed locally, so they can differ.

Further per-comment keys written by magit-dash (all optional, preserved by writers that do not know them):

| Key              | Type    | Meaning                                                                                  |
|------------------+---------+------------------------------------------------------------------------------------------|
| =diff_side=      | string  | =LEFT= or =RIGHT=, from the thread's =diffSide=. Submit sends it as =side= (and =startSide= for a range). GitHub-owned: overwritten on merge. |
| =local_resolved= | boolean | Set by a local resolve action (=magit-dash-review-append-reply= with resolve). Cleared when submit resolves the thread, or when GitHub reports it resolved or reopened. |
| =gh_reopened=    | boolean | Set by merge when the last known GitHub state was resolved and GitHub now reports the thread open; cleared when GitHub resolves it again or a local resolve action runs. |
| =gh_missing=     | boolean | Set by merge on a thread with a =gh_thread_id= that a fresh, complete (not truncated: fewer than 50 threads came back) remote fetch did not return, i.e. deleted on GitHub. Cleared when the thread matches again. Submit skips replies and resolution for it (with a message). |
| =status=         | string  | Submit sets =sent= on every thread it posted; a =sent= or =draft= thread is never posted again. |

Replies: submit sets =gh_comment_id= and =status= =sent= on each reply it posted. Reply ids hash in a counter and a random number, so two replies made in the same second differ.

* Merge behaviour

** Implemented (=magit-dash-review-json-merge=, aliased as =magit-dash-review--merge-json=)

Implemented by the json-adapter task in =magit-dash-review-json.el=. =magit-dash-review.el= keeps the old function names as aliases.

- Matching, first hit wins, each local thread used at most once: (1) GitHub node id (=remote_id= or =gh_comment_id= of either side), (2) =cr_id=, (3) =gh_thread_id=, (4) SHA-1 of path, /all/ line numbers (start and end) and body (empty bodies never match). So a local thread that already carries the remote's =gh_thread_id= wins over an identical-looking one without it. A candidate whose =gh_thread_id= differs from the remote thread's is never matched, so two identical comments on different GitHub threads stay apart. The hash tier skips candidates with =origin= =local= or =agent= unless the comment being matched has that same origin, so locally authored comments stay whole.
- The result starts as a copy of the existing file, so unknown top-level keys (=code_review=, =x_foo=), unknown =magit_dash= keys, =viewed= and =verdict= survive. =format=, =root=, =base=, =head= and =magit_dash= (provider, repo, number, url, refs, =synced_at=) are rewritten from the new metadata when given.
- A matched thread starts as a copy of the /local/ thread. These GitHub-owned keys take the remote value: =gh_thread_id=, =gh_comment_id=, =gh_resolved=, =origin=, =path=, =lines=, =blob=, =author=, =at=, =body=, =outdated=. A key in that list that the remote thread omits (=outdated=, =blob=, =lines=, ...) is removed from the merged thread, so a thread that stops being outdated clears. Every other key (=id=, =cr_id=, =remote_id=, =status=, unknown keys such as =x_bar=) keeps the local value and falls back to the remote one only when local has none. The merge result shares no structure with its inputs (deep copies), so mutating it never changes the existing table or the remote threads.
- Sticky-resolved: =resolved= is =true= if either side is resolved. Consequence: a thread that is resolved locally stays resolved after GitHub re-opens it (=gh_resolved= does record GitHub's state), until the local file is edited. A thread resolved only on GitHub becomes resolved locally. Submit does not treat that sticky state as an instruction: a thread whose last known GitHub state was resolved and which GitHub now reports open gets =gh_reopened= =true= (and loses =local_resolved=), and submit does not call =resolveReviewThread= for it. Intent to resolve is a =local_resolved= marker, or a locally resolved thread that GitHub never had resolved and that was not reopened.
- Deleted threads: with =:threads-complete= in the remote metadata (sync passes it when fewer than 50 threads came back; review-pr only when it got some), an unmatched local thread carrying a =gh_thread_id= gets =gh_missing= =true=.
- Replies: all remote replies, then local replies without a =gh_comment_id= (unpublished), then published local replies the remote list lacks, kept and flagged =gh_missing= =true= because the remote fetch may be truncated (a reply deleted on GitHub therefore also lingers, flagged). Published local replies the remote list has are replaced by the remote copies.
- Order: comments keep their existing local order (a merged thread stays in place); unmatched remote threads are appended in remote order.
- Different repo: if the existing table's =magit_dash.repo= differs from the incoming repo, the existing table is ignored (with a message) and a fresh one built. Review files are named =pr-N.json= for legacy files and =pr-OWNER_NAME-N.json= otherwise (=magit-dash-review-file= with a repo argument); a legacy =pr-N.json= is used only when its recorded repo matches; one with no =magit_dash.repo= cannot be verified for any repo, so it is ignored (message) and the repo-keyed name is used.
- Timestamps: =at= is copied from GitHub's =createdAt= and omitted when GitHub gives none; the merge never invents a time, so merging the same input twice is idempotent (only =magit_dash.synced_at= changes).
- Ids: =id= is the first 12 hex digits (48 bits) of the SHA-1 of the GitHub node id, stable across sessions; a comment with no node id gets a random 12-digit id.
- Unmatched remote threads are added as they are; unmatched local threads are kept whole. A remote thread that arrives between two merges is matched by =gh_thread_id= on the next one and appears once.

** Export and import

- =magit-dash-review-json-export= =(REPO . NUMBER)= reads the review file (=magit-dash-review-json-source-function=), deep-copies it, and overlays code-review's =cr_id= and =remote_id= onto matching threads only where the file has none; =status= from the seam wins whenever it is non-empty and different, so a comment the seam reports =sent= is never left as =draft=. Code-review comments with no match are appended with =origin= =code-review=. Missing =code_review= keys (=pullreq_id=, =account=, =analysis=) are filled from code-review. Replies, resolved state, verdict and viewed always come from the file.
- =magit-dash-review-json-import= TABLE mirrors comments and the verdict into code-review and returns =(:added N :updated N :skipped N :verdict-failed N :assigned ALIST)=. Unchanged comments (same body, resolved state and reply content: author, time, body) are skipped, so a second import is a no-op; status is ignored because code-review assigns it. A write that signals (transport failure, or no supported API) counts as skipped and never touches TABLE, so drafts stay drafts. An error from the seam's =comments= read is caught, messaged, and counts every comment as skipped (nothing is written, so nothing is duplicated). The verdict is read through the seam first and written only when it differs; a failed verdict write counts in =:verdict-failed=. TABLE needs =magit_dash.repo= and =number=.
- =:assigned= is a list of =(INDEX . CR-ID)= for comments of TABLE that had no =cr_id= but are now stored under one. =magit-dash-review-json-apply-assigned= sets them on TABLE; the mirror (=magit-dash-review--maybe-mirror=) does that and rewrites the review file, so a later edit of an id-less draft updates the stored comment instead of adding a second copy. Import itself never mutates TABLE.
- Export with no review file (nil source) fills =magit_dash.repo= and =number= from PR-KEY, so its result can be imported. The default source function returns nil, with a message, when the file's =magit_dash.repo= is not the PR-KEY repo, or when reading fails.
- Seam values are JSON tables: hash tables, vectors, strings, numbers, =t=, =nil=, =:false=. Lists are tolerated in what the seam returns: export converts every non-empty list to a vector, so the exported table always serializes. =magit-dash-review-json-deep-copy= accepts both shapes.
- Round trip: export, import, export yields identical JSON for tables whose comments already carry =cr_id= (a comment code-review numbers on first write gets its =cr_id= on the next export, or at once in the file when mirrored).
- Zero-based hunk-index key convention for =code_review.analysis.<path>= is unchanged and still unconfirmed by code, since nothing writes =analysis= yet.

** Submit (=magit-dash-review-submit=, legacy GraphQL path)

- Requests: every GraphQL call sends query and variables as one JSON body in a temporary file (=gh api graphql --input FILE=), never as =-F key=value= fields. =-F= reads =@file= values from disk and coerces numbers, =true= and =null=, so review text (reply bodies, owner, repo, ids) could otherwise read local files or change type. A test asserts no =-F= reaches gh and that bodies such as =@/etc/hostname=, =123= and =null= arrive as literal strings. (=magit-dash-pr-fetch-threads-graphql= in =magit-dash-pr.el=, used by sync and review-pr, still passes owner and repo with =-F=; it is outside the review files.)
- Persistence: the file is written after every successful mutation (each chunk of new threads, each reply, each resolution), so a failure part way leaves what was sent recorded and a repeated submit sends only the remainder. New threads are posted in chunks of 40 as separate reviews (all =COMMENT= except the last, which carries the verdict event and summary); each returned comment is matched to its local thread on path, line and body, never by position, then stamped (=gh_thread_id=, =gh_comment_id=, =origin= =github=, =status= =sent=). A posted thread GitHub returned no matching comment for is still marked =sent= (message) and is linked by the next sync. The one narrow window left is a crash between GitHub answering and the write.
- Errors: a failing reply or resolution on one thread is collected; later replies on that thread are not tried (order), other threads still run, and the run ends with one error listing them. A failing review chunk aborts, since nothing after it would be coherent.
- Verdict: =approved= sends =APPROVE=, =changes= =REQUEST_CHANGES=, =comment= =COMMENT=; any other state sends nothing (message). After sending, =verdict.submitted_state=, =submitted_head= and =submitted_at= are stamped; a verdict is sent again only when its state or =head= no longer match them. =commitOID= is =magit_dash.head_oid= (else the PR's current head). =APPROVE= and =REQUEST_CHANGES= are refused with a =user-error= when =magit_dash.head_oid= or =verdict.head= differs from the PR's current =headRefOid=; sync and re-review first. Nothing is posted in that case.
- Replies and resolutions skip =gh_missing= threads.
- Reading: submit reads the file with =magit-dash-review-json-read-for-write=; see Encoding for the backup fallback.

** Which writers protect a modified buffer

Every writer (=append-reply=, draft insertion, =promote-draft=, EARS projection, =submit=, the hitl batch flush, the code-review mirror, =magit-dash-review-pr=, =worktree-diff=, =sync= and worktree relocation) refreshes a visiting buffer through one helper, =magit-dash-review-json-refresh-visiting-buffer= (alias =magit-dash-review--refresh-visiting-buffer=): a clean buffer is reverted (=diff-review-refresh= in a =diff-review-mode= buffer), a modified one is never reverted or refreshed (message; the file on disk is still updated and saving the buffer later asks about the newer file). With =magit-dash-review-json-modified-buffer-action= =save= (default =skip=) the modified buffer is saved first instead. =sync= and =review-pr= go further and do nothing to a file whose buffer is modified. Both re-read the file after their network calls, so edits made meanwhile are merged.

** Flag

=magit-dash-review-use-code-review-adapter= (default nil) makes =magit-dash-review-pr= and =magit-dash-review-sync= import the merged table into code-review. =magit-dash-review-submit= still uses its GraphQL mutations (see Submit); routing it through code-review is the route-submit task.

* Encoding

Files are UTF-8: written with =utf-8-unix= and read as =utf-8=, so non-ASCII text round-trips as itself. Writing is atomic: the JSON goes to a temporary file in the same directory which is renamed over the target. A symlinked file is resolved first (the link stays a link, the target is replaced and gets the =.bak=); the old file's modes are kept, a new file is 0600; =FILE.tmp-*= leftovers older than a day are removed. The previous file is copied to =FILE.bak= only when it parses as JSON, so =.bak= is always the last good file and a corrupt file never replaces it. Reading a file that does not parse falls back to a parseable =FILE.bak= with a loud message and sets =magit-dash-review-json-last-read-fallback=; if the backup is corrupt too the read signals. Writers read through =magit-dash-review-json-read-for-write=, which asks =yes-or-no-p= before building on a fallback and signals a =user-error= when declined. =magit-dash-review-sync= merges against a fresh read taken after its network calls and does nothing (with a message) when the review file is open in a modified buffer. The worktree recorded in a review file is only used when it belongs to the same repository (same git common directory); otherwise the main checkout is used. Moving a worktree (=magit-dash-pr--move-worktree=) rewrites =root= and =magit_dash.worktree= in the review files that named it.

Parse with =:object-type 'hash-table :array-type 'array :null-object nil :false-object :false=; serialize with the matching =:null-object nil :false-object :false=. Empty =viewed= is ={}=, empty =replies= is =[]=.

* code-review public API audit (json-adapter task)

Audited only part of =~/src/code-review=: =code-review-db.el=, =code-review-db-reviewed.el=, =code-review-comment.el=, =code-review-github.el=, =code-review-actions.el=, =code-review-local.el= and =code-review-viewed.el=. Other files were not checked, so a gap below may have an answer there. Only non =--= functions count as public.

Public and relevant:

| Function | What it gives |
|----------+---------------|
| =code-review-db-search= OWNER REPO NUMBER | A closql =code-review-db-pullreq= object (saved, unfinished review). Comments are in its =raw-comments= slot, read only through =oref=, which is closql. |
| =code-review-db-get-pullreq=, =-get-buffer=, =-get-comment= | Closql objects, resolved through the dynamic variable =code-review-db--pullreq-id=. |
| =code-review-db-update= OBJ | Writes a closql object back. |
| =code-review-db-delete-raw-comment= IDENTIFIER | Deletes one raw comment by =internal-id= or =databaseId=. The only public comment mutation. |
| =code-review-db-all-unfinished=, =-cleanup=, =-local-pr-p= | Listing, cleanup, local-PR predicate. |
| =code-review-submit-comments=, =-submit-request-changes=, =-submit-lgtm=, =-submit-only-replies=, =code-review-submit-approve= | Interactive send paths for the current review buffer: verdict maps to =COMMENT=, =REQUEST_CHANGES=, =APPROVE=. They need the live review buffer and dynamic db context. |
| =code-review-send-review=, =-send-replies=, =-new-code-comment=, =-toggle-resolved=, =-update-comment= (generic methods) | Transport through ghub for a pullreq object and prepared submit objects. |
| =code-review-comment-add=, =-comment-add-or-edit=, =-edit-remote-comment-at-point=, =-viewed-toggle= | Interactive, act at point in the review buffer. |

Gaps (no supported data API, so the adapter cannot do these without reaching into closql or private functions):

1. Reading comments as data. Raw comments sit in the =raw-comments= slot of a closql object; there is no accessor that is not =code-review-db--pullreq-raw-comments= (private). A possible but undocumented path exists: =code-review-db-search= returns the pullreq object, =oref= reads =raw-comments=, and =oset= followed by =code-review-db-update= writes it back. The stored format is undocumented, and there is no draft-comment upsert, so the caller would have to build and merge raw comment records itself.
2. Writing or updating a local (draft) comment programmatically. Local comments are made by =code-review-comment-handler-commit= methods acting on a section object, and stored by private =code-review-db--pullreq-raw-comments-update=, =code-review-comment--save-draft=.
3. Recording a verdict. There is no stored verdict; the event is an argument of the interactive submit commands.
4. Reviewed (viewed) state. =code-review-db-reviewed.el= has only =code-review-db--reviewed-*= functions; the only public entry is the interactive =code-review-viewed-toggle=.
5. =pullreq_id=, account and analysis (criteria, risk rank, test-impact tags) have no data-level accessor either.

Decision: every call into code-review goes through =magit-dash-review-json-code-review-function= (a defcustom), with ops =comments=, =pullreq=, =write= and =verdict= documented in its docstring. The default implementation returns nothing for reads and signals for writes, so with it import skips everything and leaves comments as drafts, visibly (a message names the missing API). Closing the gap means either a small public data API in code-review (=code-review-comments=, =code-review-comment-upsert=, =code-review-verdict-set=), or a seam implementation here that wraps the interactive commands or the =code-review-db-search= plus =oref=/=oset= plus =code-review-db-update= path above. The choice is the user's and is not made; the default seam implements none of them.
